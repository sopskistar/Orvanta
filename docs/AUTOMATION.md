# Phase 2: coded integration checklist (not operational)

The public site works without this phase. `src/lib/enquiries.ts` defines the future enquiry, trusted mapping and processing-state contracts. No webhook route, database, email delivery, retry job, live call or booking tool is connected. Do not add any working-service claim until genuine tests provide evidence.

## Inputs still needed

An authorised Retell workspace and agent, an API key marked for webhook verification, agreed tenant/agent mapping and recipient, a Neon project/connection string, an email-provider account with verified sender domain, deployment capable of running server endpoints and durable scheduled work, and an agreed record-access/retention policy. Secrets belong in server deployment settings, never `NEXT_PUBLIC_*` variables. A sales Calendly URL and customer-service booking permissions are separate inputs.

## Reviewable changes, in order

1. **Endpoint and authenticity.** On a server-capable deployment (remove `output: 'export'` for a Next server or use a separate backend), add a bounded POST endpoint for `call_analyzed`. Read and verify the untouched raw body before parsing JSON. Use Retell's documented `Retell.verify(rawBody, apiKey, signature)` and the `X-Retell-Signature` header. Reject absent/invalid signatures; use the webhook-badged key. Enforce content type, actual byte limits even without Content-Length, schema, event and agent mapping. See [official security documentation](https://docs.retellai.com/features/secure-webhook). Recheck the SDK/API version when implementation begins.
2. **Trusted mapping.** Map verified provider context and agent ID to one configured tenant, notification recipient and time zone on the server. If workspace identity is not present in a verified payload, derive it from the endpoint/key's configured workspace rather than trusting caller metadata. Reject unknown agents. Callers and extracted fields cannot supply recipients, tenant IDs, sender identities or tool permissions.
3. **Persistence and deduplication.** In one Neon transaction insert the minimal enquiry and an outbox row. A unique `(client_id, event, call_id)` key prevents duplicate lifecycle notifications. Return a 2xx only after durable acceptance; retryable storage failures return non-2xx. The current Retell [webhook overview](https://docs.retellai.com/features/webhook-overview) documents duplicate deliveries and `event + call_id` deduplication for lifecycle events. Do not treat its retries as an email outbox.
4. **Transactional delivery.** A worker claims persisted rows with a lease/locking strategy, renders a text-first escaped summary and calls the configured email provider with a stable idempotency key. Save its message ID and acceptance state. Provider API acceptance is not inbox delivery. [Resend's idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys) are time-limited, so database uniqueness is still required. Handle uncertain timeouts with reconciliation; do not blindly resend after the provider's key window expires.
5. **Durable retry and visibility.** Persist attempt count, next attempt, safe error code and a terminal/dead-letter state. Use bounded backoff, claim expiry and a documented scheduled-worker trigger suitable for the selected hosting plan. A protected retry endpoint must require a server secret, atomically claim only eligible jobs, bound its batch and be idempotent. Provide a manual authenticated retry command as well. Never return from a serverless request and rely on an untracked background promise. Do not introduce a paid scheduler implicitly.
6. **Private records.** If an admin view is later requested, require authentication and enforce client isolation on every query and record URL. Do not log full transcripts, recordings, phone numbers or email contents. Store only what is necessary; agree retention and access separately.

## Data rules

Preserve `customer_name`, `callback_number`, `service_requested`, `zip_code`, `property_details`, `preferred_date`, `cleaning_notes`, `callback_preference`, `follow_up_needed`. Phone and ZIP remain strings (including leading zeros and country prefixes). Missing data stays null/absent; never fill it with guessed values. An absent follow-up flag is not automatically false. Cleaning dates and callback times/preferences remain separate. A preferred cleaning date is not a booking. Keep the source time zone and avoid silently interpreting ambiguous dates.

## Synthetic verification before connection

Use local provider doubles and authorised test accounts only. Required cases: valid signed post-call event; absent, invalid and stale signatures; byte-different raw JSON; unknown agent/tenant; malformed or oversized body; missing and partial extraction; leading-zero ZIP/phone strings; duplicate delivery including concurrent requests; database rollback; provider rejection; timeout after provider acceptance; scheduled retry and expired lease; dead-letter visibility; worker crash/restart; tenant access denial. These tests must not send to uninvolved people. Then use one agreed test recipient, verify receipt and matching enquiry details, and distinguish acceptance, delivery and bounce evidence.
